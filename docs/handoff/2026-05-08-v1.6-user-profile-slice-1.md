## What this branch does

Adds the v1.6 **architect user profile** — seven preference "knobs" the architect's stages read to adapt their behavior — and proves the integration end-to-end through one knob (`testStrictness`).

The remaining six knobs are persisted, validated, and exposed via the admin REST API but **not yet consumed** by any stage. That's deliberate; this slice establishes the pattern, future slices wire each remaining knob the same way.

```
profile (sqlite)  ─►  UserProfileStore.getDefault()   per cycle
                            │
                            ▼
                  runBuildingStage({ ..., testStrictness })
                            │
                  ┌─────────┼─────────┐
                  ▼         ▼         ▼
              must-pass    warn    advisory
              soft_fail    ok      ok
                          (with [WARN]/[ADVISORY] prefix on testSummary)
```

## The seven knobs

All persisted in `user_profile` table (CHECK-constrained enums) with a seeded `'default'` row. Order matters in the wizard.

| Column | Values | Default | Wired into a stage? |
|---|---|---|---|
| `plan_verbosity` | `brief` \| `standard` \| `detailed` | `standard` | ❌ pending |
| `auto_approve_threshold` | `never` \| `low-risk-only` \| `aggressive` | `never` | ⚠ written by mode preset, not yet read by any stage |
| `test_strictness` | `must-pass` \| `warn` \| `advisory` | `must-pass` | ✅ done (slice 1) — `runBuildingStage` |
| `gate_policy` | `every-stage` \| `plan-only` \| `merge-only` | `every-stage` | ✅ done (slice 2) — daemon `isApprovalRequired` |
| `tone` | `terse` \| `standard` \| `explanatory` | `standard` | ❌ pending |
| `iteration_patience` | `stop-at-2` \| `stop-at-5` \| `stop-at-budget` | `stop-at-budget` | ❌ pending |
| `risk_posture` | `conservative` \| `balanced` \| `experimental` | `balanced` | ❌ pending |

Defaults for `auto_approve_threshold` and `gate_policy` were re-aligned in slice 2 so a fresh-install profile derives to mode `'hands-on'` — preserving the historical "safest by default" contract that the legacy `GET /status` returned.

## Design decisions baked in

1. **String-prefix carrier for `warn` / `advisory`.** Failed tests under non-strict modes return `kind: 'ok'` with `testSummary` prefixed `[WARN]` or `[ADVISORY]`. Zero schema changes; the prefix travels through `cycleStore.terminate({testSummary})` to the UI. Easy to revisit if analytics need a typed flag.
2. **Per-cycle profile read, not per-daemon-construction.** `UserProfileStore.getDefault()` runs inside the `runBuild` closure on every cycle. One SQLite point-lookup per ~60s tick. Live edits to the profile via the admin API take effect on the next cycle without a daemon restart.
3. **Optional `testStrictness?` with `'must-pass'` fallback.** Backward compatibility for free — every existing test, every existing call site needed zero changes.
4. **Admin auth via global `onRequest` hook.** New route file added zero auth code. The hook in `packages/core/src/server.ts` handles `/api/admin/*`.

## Quick reference: read the profile from inside a stage

```ts
import { UserProfileStore } from '@coastal-ai/core/architect/user-profile/store'
// at daemon construction:
const userProfileStore = new UserProfileStore(architectDb)

// inside a runX closure:
const profile = userProfileStore.getDefault()
// profile.tone, profile.testStrictness, profile.iterationPatience, ...
```

The `'default'` row is created on first `openArchitectDb()` call — no setup step required. Live edits via `PUT /api/admin/architect/user-profile` take effect on the next cycle.
